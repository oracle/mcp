# Code quality

Use this guide when implementing or reviewing server/library changes. It explains the requirements owned by [root editing rules](../AGENTS.md#editing-rules) and [BEST_PRACTICES](../BEST_PRACTICES.md#code-quality). Read the applicable [component guide](agent-development.md#selected-component-context) before judging a package's interfaces. Examples illustrate review decisions; they do not describe every server's current compliance.

## Review criteria

Prefer the smallest implementation that satisfies the requested behavior and preserves the package's contracts. Evaluate concrete correctness and maintenance costs rather than guessing whether code was generated by AI.

| Concern | Reviewable expectation |
| --- | --- |
| Abstractions | Introduce a layer for an actual boundary, repeated behavior or demonstrated variation. A factory hierarchy for one fixed client needs a reason beyond possible future extensions. |
| Wrappers | A helper should name meaningful behavior, adapt an interface, enforce an invariant or provide a useful seam. A function that merely renames another function adds navigation without explaining behavior. |
| Shared logic | Reuse owning libraries, especially [Common authentication](authentication.md). Package-owned client type, retry policy and lifecycle remain local; similar spelling alone does not make behavior shareable. |
| Failures | Distinguish an empty successful result from a failed request. Handle expected exceptions at the boundary where they can be interpreted; propagate unexpected failures through the package's error contract. |
| Types and suppressions | Model known inputs/results explicitly. Explain a narrow type/lint suppression at its actual incompatibility; do not suppress an entire module to avoid understanding an error. |
| Names and comments | Name domain behavior. Comments explain constraints, tradeoffs or non-obvious service behavior; they need not narrate assignment and iteration. |
| Change scope | Keep formatting, import ordering, cleanup and dependency changes limited to what the requested behavior needs. |

A short adapter can be valuable: converting an SDK response into the documented public model keeps SDK details outside a tool's contract. Its value is the conversion boundary, even if its body is one line. A wrapper that forwards the same arguments and return value without such a responsibility is usually unnecessary. Likewise, consolidating several authentication paths into Common is justified reuse; building a generic framework around one tool is speculative.

An exception handler that returns `[]` for any SDK failure makes an outage look like an empty collection. Returning `[]` is appropriate when a successful response contains no items. An expected not-found result may have its own documented meaning; test that meaning and avoid catching unrelated authorization/network failures as not-found.

## Applying the criteria

Trace inputs through validation, authentication, service invocation and result shaping. Ask whether the new layer or fallback improves that path. Preserve useful native patterns rather than refactoring the package to match a preferred style.

A review finding should identify the path/line, evidence, consequence and bounded remedy. Explain why duplicated credential precedence can diverge, or why a fallback hides failure; avoid a finding that merely calls code “slop.” Optional readability suggestions should be separate from defects.

Use [test quality](test-quality.md#review-criteria) to check the asserted behavior, [FastMCP contracts](fastmcp.md#tool-contracts) for protocol-facing changes, and [the validation map](agent-development.md#validation-map) for checks. Source examples and test definitions are leads; only recorded executions establish passing results.
