## MODIFIED Requirements

### Requirement: Profile-aware startup preflight
Every profile SHALL verify access to its execution namespace and the pod lifecycle and exec operations it requires. Cluster-scoped Namespace and Kata RuntimeClass access checks SHALL name exactly the configured objects, and in-cluster example RBAC SHALL use matching `resourceNames` restrictions where supported. Both in-cluster profiles SHALL additionally require separate-namespace identity, cross-namespace self-access checks, acceptance of the conforming pod shape, and rejection of one reviewed negative variant for every security-critical base-pod invariant. The example admission policies SHALL accept every documented in-range CPU, memory, ephemeral-storage, and memory-backed `/tmp` configuration generated by the trusted pod builder while requiring equal resource requests and limits, and SHALL reject missing, unequal, malformed, or out-of-range resource values. `kata-in-cluster` SHALL additionally verify the exact named RuntimeClass handler and reject a wrong-RuntimeClass variant. A successful probe set SHALL be reported only as `reviewed-variants-rejected`; local development SHALL report `unverified` when its cluster accepts a reviewed unsafe variant.

#### Scenario: Standard in-cluster admission
- **WHEN** `in-cluster` preflights admission
- **THEN** the conforming standard-runtime pod SHALL be accepted and negative variants for every reviewed base-pod invariant SHALL be rejected
- **AND** startup SHALL fail if the effective admission path permits any reviewed weakening

#### Scenario: Kata admission
- **WHEN** `kata-in-cluster` preflights admission
- **THEN** the conforming Kata pod SHALL be accepted and all shared plus wrong-RuntimeClass variants SHALL be rejected
- **AND** a missing, unauthorized, or mismatched configured RuntimeClass SHALL fail startup

#### Scenario: Reviewed non-default resource configuration
- **WHEN** either in-cluster profile uses documented non-default or boundary values for CPU, memory, ephemeral storage, or memory-backed `/tmp`
- **THEN** the generated conforming pod SHALL be accepted by the example admission policy
- **AND** otherwise-equivalent pods with unequal requests and limits or values outside any documented range SHALL be rejected

#### Scenario: Exact cluster-scoped authorization
- **WHEN** an in-cluster profile checks authorization to read its execution Namespace and, for Kata, its configured RuntimeClass
- **THEN** each self-access review SHALL include the exact object name
- **AND** the example cluster role SHALL restrict each corresponding `get` rule to that same object through `resourceNames`

#### Scenario: Local cluster lacks production admission
- **WHEN** `local-development` can perform the required pod lifecycle but accepts one or more reviewed unsafe variants
- **THEN** the profile MAY run for development with `admissionPreflight` reported as `unverified`
- **AND** it SHALL remain ineligible for in-cluster or production assurance claims

### Requirement: Complete in-cluster deployment assets
Each standard and Kata in-cluster example bundle SHALL deploy a trusted host in a
namespace separate from the execution namespace, using the trusted host service
account, its exact Kubernetes profile, and downward-API values for its namespace,
pod name, and pod UID. A Kata host SHALL additionally configure the exact reviewed
RuntimeClass and handler. Each bundle SHALL deploy the independent cleanup-only
reconciler under its distinct identity. The trusted host alone MAY mount the OCI
credential Secret; the execution runner and cleanup reconciler SHALL receive no
OCI credential mount. The host and runner images SHALL be immutable digest
references, and the runner digest configured for the host SHALL be the exact
digest required by that profile's admission policy. Example assets SHALL not
contain credential material.

#### Scenario: Standard trusted-host topology
- **WHEN** an operator applies the standard in-cluster example bundle after
  supplying reviewed image digests and a host-namespace OCI credential Secret
- **THEN** it SHALL create the trusted host Deployment with only its required
  in-cluster profile, runner, OCI configuration, and downward-API identity
  settings
- **AND** the host Secret SHALL be mounted read-only only by that Deployment
- **AND** the runner and cleanup reconciler SHALL not receive OCI configuration
  or credential mounts

#### Scenario: Runner image is admission-aligned
- **WHEN** the standard trusted host is configured with its runner image digest
- **THEN** the standard admission policy SHALL require exactly that same runner
  image digest for execution pods
- **AND** a changed host runner digest without a matching admission-policy
  update SHALL fail manifest-contract validation

#### Scenario: Kata trusted-host topology
- **WHEN** an operator applies the Kata in-cluster example bundle after
  supplying reviewed image digests, an exact reviewed RuntimeClass/handler, and
  a host-namespace OCI credential Secret
- **THEN** it SHALL create the trusted host Deployment with the
  `kata-in-cluster` profile, the exact RuntimeClass and handler, runner image,
  OCI configuration, and downward-API identity settings
- **AND** its runner image digest SHALL match the Kata admission policy
- **AND** the host Secret SHALL be mounted read-only only by that Deployment
- **AND** the runner and cleanup reconciler SHALL not receive OCI configuration
  or credential mounts

### Requirement: Profile-aware orphan reconciliation
The trusted host SHALL reconcile expired managed pods for every Kubernetes profile while it is running. Both in-cluster profiles SHALL support an independently deployed cleanup-only reconciler with get, list, watch, and delete authority but no create or `pods/exec` authority. Reconciliation SHALL delete only expired pods matching trusted managed labels and profile metadata, SHALL preserve unrelated, malformed, and non-expired pods, and SHALL bound and isolate deletion and confirmation failure per candidate so later candidates are still processed. Each candidate deadline SHALL abort its underlying Kubernetes delete and confirmation requests so timed-out work cannot remain active or accumulate across candidates or reconciliation passes. Each pass SHALL report sanitized aggregate success and failure counts without raw Kubernetes errors or pod names in diagnostics.

#### Scenario: Expired local development pod
- **WHEN** the local host starts or reaches its reconciliation interval and finds an expired pod it manages
- **THEN** it SHALL delete and confirm that pod
- **AND** it SHALL preserve unrelated or non-expired pods

#### Scenario: First expired pod cannot be deleted
- **WHEN** deletion or confirmation for the first expired managed pod fails or exceeds its per-pod bound while later expired pods are eligible
- **THEN** reconciliation SHALL record that candidate as failed and continue attempting every later candidate in the same pass
- **AND** diagnostics SHALL report aggregate failure without exposing the failed pod name or raw API error

#### Scenario: Kubernetes request never settles
- **WHEN** a candidate delete or confirmation request remains unresolved through its per-pod deadline
- **THEN** reconciliation SHALL abort that request before proceeding beyond the candidate
- **AND** later candidates and future reconciliation passes SHALL not accumulate active requests from the timed-out candidate

#### Scenario: All in-cluster hosts unavailable
- **WHEN** all trusted host replicas are down and an in-cluster managed pod expires
- **THEN** the independent reconciler SHALL delete and confirm the expired pod
- **AND** it SHALL not gain create or exec authority
