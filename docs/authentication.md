# Shared authentication for MCP servers

This is the repository-level integration guide and adoption ledger for the shared Python authentication package, `oracle-mcp-common`. It explains the requirements for servers using OCI credentials and how to apply the package within server-owned client/transport code. [Root quality rules](../AGENTS.md#mcp-server-quality-validation) and [BEST_PRACTICES](../BEST_PRACTICES.md#oci-sdk-authentication) establish the existing requirements; [Common's README](../src/common/README.md#authentication-module) owns the detailed public API, supported modes and input contracts. The ledger describes current source, separately from required behavior and executed validation.

Apply root and applicable component instructions when following source links. The [Common guide](../src/common/AGENTS.md) supplies library orientation; the [component map](agent-development.md#selected-component-context) supplies each server's broad guide. Local topic explanations, such as [Compute authentication](../src/oci-compute-mcp-server/docs/authentication.md), describe differences without replacing the shared requirements.

## Requirements and responsibility boundaries

- Python MCP servers that construct OCI SDK clients must declare a compatible bounded `oracle-mcp-common` dependency and use `build_auth_context()` for configured credential modes. Do not duplicate credential resolution, profile parsing, input precedence or signer construction in server code.
- HTTP servers that authenticate OCI IAM/IDCS callers and exchange request tokens must use `build_idcs_http_auth(required_scopes)` for provider policy and `context_for(access_token.token)` for each authenticated request. The server retrieves the request token explicitly. Host/port settings select listener configuration; they must not select credentials.
- The server owns service client type, listener startup, `mcp.auth` assignment, user-agent derivation, retry/circuit-breaker policy and client lifecycle. HTTP-derived signers and clients remain caller-specific; do not cache them globally or reuse them across callers.
- Preserve the root-required metadata-derived `additional_user_agent` on every supported SDK client path. CLI-backed servers use the corresponding `OCI_SDK_APPEND_USER_AGENT` process environment requirement.
- If Common lacks an OCI authentication capability needed by an MCP server, **update the shared package to support that use case**, including its public contract and tests, then integrate it in the server. Record the missing behavior and affected consumers before implementing it; do not create another server-local authentication implementation to fill the gap. An existing legacy path is not an approved exception.

This Python package does not automatically replace JavaScript/Java SDK providers, database credentials, GoldenGate deployment Basic auth or other service-specific protocols. Their current paths are recorded below. Keep a genuinely shared OCI credential capability in Common; keep service-specific authorization and connection behavior with its owner. A future cross-runtime interface requires its own design rather than an assumed Python import.

## Integrate configured OCI credentials

1. Declare a bounded dependency compatible with the APIs the server uses. Root guidance states `oracle-mcp-common>=0.1.0,<0.2.0`; current adopters declare `>=0.1.2,<0.2.0`. Inspect the [Common manifest](../src/common/pyproject.toml) and target manifest/lock for actual install constraints. The existing Common README/manifest version discrepancy remains in the [gap register](agent-development.md#known-gaps); do not infer resolved dependencies from a documentation example.
2. Call `build_auth_context()` where the server resolves configured OCI credentials. Pass `AuthOptions` only for intentional server overrides. Merge the returned config with the metadata-derived user agent and pass its signer to each OCI client:

```python
from oracle_mcp_common import build_auth_context

# In the server's client factory; oci and _ADDITIONAL_UA are server-owned.
auth_context = build_auth_context()
config = {**auth_context.config, "additional_user_agent": _ADDITIONAL_UA}
client = oci.object_storage.ObjectStorageClient(config, signer=auth_context.signer)
```

3. Reuse Common's [supported modes](../src/common/README.md#select-an-authentication-type), [precedence](../src/common/README.md#configuration-precedence), [direct-profile token rules](../src/common/README.md#profile-backed-authentication) and [secret input contracts](../src/common/README.md#type-specific-inputs). `auto` classifies the selected profile; it does not probe principal environments. Explicit principal modes and service-bearer UPST are documented by Common. Do not assume every server in the ledger already supports them.
4. Preserve server-specific client/lifecycle policy. Review the corresponding tests and user-agent assertions, then update native configuration documentation and the ledger when implementation changes.

API is a CLI integration: it uses Common's resolution/profile helpers, then invokes OCI CLI rather than constructing an SDK client from `AuthContext`. Its [source](../src/oci-api-mcp-server/oracle/oci_api_mcp_server/server.py) owns the CLI mode map, `OCI_CLI_AUTH` handling and supported-mode limitations. That use of shared helpers does not make every Common SDK mode available through the CLI.

## Integrate HTTP caller authentication

Build provider policy once at startup, then use an explicit token to create a request context and client. This is the intended integration shape, not a runnable standalone server or a claim that all current adopters follow it:

```python
from fastmcp.server.dependencies import get_access_token
from oracle_mcp_common import build_idcs_http_auth

# Server startup: choose the scopes required by this server.
http_auth = build_idcs_http_auth(required_scopes)
mcp.auth = http_auth.provider

# Authenticated request: retrieve and pass this caller's token explicitly.
access_token = get_access_token()
request_auth = http_auth.context_for(access_token.token if access_token else None)
config = {**request_auth.config, "additional_user_agent": _ADDITIONAL_UA}
client = oci.object_storage.ObjectStorageClient(config, signer=request_auth.signer)
```

Use [Common's HTTP contract](../src/common/README.md#http-idcs-authentication) for provider inputs, URL validation, region handling and ownership. Common does not inspect host/port, start a listener, retrieve FastMCP request context or construct service clients. Server-native scopes, callback registration, inbound authorization and listener setup remain server responsibilities. Keep outbound service-bearer UPST distinct from inbound HTTP request-token exchange.

Cloud currently uses these Common HTTP APIs but its local credential dispatch still checks host/port. Database and Recovery select caller auth from request-token/request context instead; Recovery also refuses local profile credentials when an initialized HTTP deployment lacks caller context. See [Recovery's auth module](../src/oci-recovery-mcp-server/oracle/oci_recovery_mcp_server/auth.py) and [native HTTP setup](../src/oci-recovery-mcp-server/README.md#http-streamable-http-deployment). Compute has a fully local provider/signer path and no Common dependency. These are descriptive differences to address in engineering work; this document changes no authentication code.

## Validation and maintenance

For an implementation change, inspect [Common auth tests](../src/common/oracle_mcp_common/tests/test_auth.py), affected server tests and the [validation map](agent-development.md#validation-map). Check supported modes, precedence, direct-profile token behavior, secret-safe failures and the exact derived user agent on every client path. HTTP integration also needs provider/input failure checks and caller-specific client behavior. Use the root-required package/shared checks for the actual change scope; record commands, source identities, discovery, coverage and results separately. Common tests alone do not validate server integration.

Maintain the ledger by checking native manifests **and** imports/call sites. A same-named local helper is not Common adoption, and a dependency alone is insufficient. For a missing shared capability, document the intended use case, extend Common with compatible APIs/tests/contracts, assess affected consumers, then update the server and its owning docs/routes. Follow existing contribution, compatibility and changelog rules.

The [context follow-up outcome](plans/assess-agent-context-2026-10-07/implementation-outcome.md) records the current source review and structural checks. The [earlier documentation outcome](plans/shared-authentication-context/outcome.md) retains its historical source identity. Native Common documentation remains the detailed API reference; this repository guide relates adoption requirements, integration responsibilities and the current server inventory.
